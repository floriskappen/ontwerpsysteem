# V1.0.0 Sol coherence audit

**Verdict: NOT READY**

The V1 direction is strong and recognisable: warm paper, ink-led hierarchy, square construction, lowercase Archivo, grown state metaphors, deterministic ambience, scoped adoption, light-paper skins, and the values-only shadcn bridge form a distinctive whole. The bundle is substantially more realistic to adopt than v0.1.1, and its deterministic gates are meaningful evidence. They do not, however, cover several contradictions in the consumer contract. Those contradictions are release-blocking because they can make a consumer implement something the system itself says is wrong.

## Evidence considered

- Read in the repository-mandated order: brief, propagation guide, all language, recipes, zoo source, and values; then the V1 handoff, roadmap, frontier preparation, readiness report, and assembled consumer bundle.
- Current non-publishing gates were re-run without changing the working tree:
  - `npm run validate`: tokens valid; reduced-motion coverage complete; atmosphere cost contract enforced.
  - `npm test`: **180 passed, 0 failed** across 16 files.
  - `openspec validate --all --strict`: **8 passed, 0 failed**.
- The accepted zoo baseline remains untouched. No screenshot, device result, visual approval, publish action, tag, release branch, version bump, or downstream pin advance is claimed here.

## Release-blocking coherence defects

### 1. The shipped motion contract argues both for and against smooth UI motion

The brief and `language/motion.md` require stepped clocks and immediate, hard-cut interactions; the consumer guide repeats “stepped timings … not smooth easings.” The shipped value layer nevertheless exposes `motion.duration.hover` (200ms), `motion.duration.transition` (240ms), and a standard cubic-bezier described as the easing for button hover and surface transitions. The shipped atmosphere also runs its grid and three blooms with `ease-in-out`, not a stepped clock.

A consumer following the language removes smooth transitions; a consumer following the declared semantic values adds them. Because token/value truth is a first principle and motion is part of the north star, this is not merely stale wording.

### 2. Complete-skin claims do not hold across the shipped effects surface

`principles.md` says every visual value originates in tokens or recipes, and V1 claims complete role-set skins. Yet `values/css/effects.scoped.css` retains the cream ink literal `rgb(31 27 22 / …)` in the breathing grid, wind streaks and motes, rain, splashes, and snow outlines. Those effects therefore do not follow a selected skin’s supplied ink role.

The main colour surface, blooms, pollen, components, borders, and focus states do reskin coherently; the remaining literal effect ink is precisely why the current result is close but not internally complete.

### 3. The newly tightened utility-mark rule conflicts with the canonical implementation

`language/type.md` reserves mono-uppercase for data and explicitly excludes prose labels. The changelog marks that rule as a breaking V1 correction. The shipped canonical zoo/component CSS still applies `typography.mark` plus uppercase to the field label (`e-post`) and theme-switch label (`theme`). Since the zoo is presented as “what correct looks like,” consumers receive opposing normative examples for a V1 breaking rule.

### 4. The three-case integration guide is not end-to-end safe as written

Two concrete path errors prevent the guide from being a reliable adoption contract:

- **Whole-app:** Case A says `tokens.css` is enough and no scope class is needed, but the only shipped component/effect styles are `components.scoped.css` and `effects.scoped.css`, whose selectors require an `.ontwerp` ancestor. Case A never explains how a whole-app consumer actually mounts those shipped classes and effects.
- **Island + shadcn:** the bundle README’s Case B quick path tells the island consumer to import `values/shadcn/adapter.css`; that file declares on `:root`. The island-safe file is `adapter.scoped.css` under `.ontwerp`. Following the quick path can leak shadcn variables into the shared document—the exact class of failure scoped V1 is meant to prevent.

The longer `AGENTS.md` mentions both adapter forms, but it does not neutralise the incorrect quick-start instruction.

### 5. The readiness evidence does not match the current strict-spec result

`docs/releases/v1.0.0-readiness.md` records **9** strict specs passing at “this exact state.” The current command reports **8 passed, 0 failed**. Green remains green, but release evidence described as exact must agree with the command it cites before it can support human approval.

## Non-blocking caveats

- The zoo is distinctive and largely faithful, but its literal botanical colophon leaf sits in tension with the brief’s instruction to express nature as behaviour rather than literal leaves or illustration motifs. It is isolated rather than systemic, so it is not a V1 distribution blocker.
- Eight weather fields ship and appear in the zoo, while named motion recipes cover only wind and rain. The data and cost envelope are clear, but recipe-level use/avoid guidance is uneven for the other six.
- The retrofit table refers to `state.mark.*`; the actual stable recipe ID is `state.mark.static`. The surrounding guidance remains understandable.
- The light-only stance is unusually clear and coherent across language, anti-goals, adapter, and integration guidance. Its limitation is intentional rather than unfinished work.

## Human checks still required

After the blockers above are reconciled and all gates are re-run, the human release approver must perform these checks; none is satisfied by this audit:

1. **Taste and north-star check:** inspect the rendered zoo and confirm that paper tooth, ink/pigment overlap, square construction, lowercase voice, grown state metaphors, and restrained atmosphere feel like Floris’s system rather than a themed generic kit.
2. **Skin check:** switch every shipped skin and confirm by eye that text, borders, controls, focus, destructive marks, grain-adjacent effects, blooms, and weather all remain harmonious and legible.
3. **Motion check:** inspect normal and `prefers-reduced-motion: reduce` modes; confirm stepped/instant behaviour in normal mode and deliberate, finished rest poses with no stranded particles or half-grown states in reduced mode.
4. **Interaction check:** keyboard-test the theme selector, segmented control, buttons, links, and fields; confirm visible focus, understandable selection, and readable labels without relying on colour alone.
5. **Responsive check:** inspect the zoo at a narrow viewport and a standard desktop viewport for clipping, hierarchy, touch-target practicality, and readable type. No device coverage is inferred here.
6. **Adoption check:** exercise the documented whole-app and island import paths in representative host pages, including an excluded subtree, a `.ontwerp-boundary`, a skin, and the scoped shadcn adapter; confirm no token, voice, component, effect, or adapter leakage.
7. **Release approval check:** review the final versioned changelog/migration notes, approve the release command sequence, and only then publish/tag/push. De Ontwerper’s pin advance and deletion of hand-maintained copies remain the separate downstream acceptance test.

Until the five coherence defects are corrected and the human checks are completed, there is no defensible V1 publish approval.
