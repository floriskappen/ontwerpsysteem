## 3. Zoo: reskin through the built output

- [x] 3.1 Delete the component-var re-link block (`--button-* … --link-underline-hover`) from `body` in `design-system/source/zoo/styles/base.css`, keeping the `--wx-bloom-*` / `--wx-pollen` baseline declarations (those are zoo-local effect vars, not built tokens).
  > Note: the `--wx-*` baseline declarations were kept but moved from `body` to a `:root` rule in the same file. Left on `body`, they would mask the retargeted `:root:has()` skin overrides (an element's own declaration beats an inherited one), silently breaking the bloom/pollen reskin — the same cascade mechanic design decision 2 documents.
- [x] 3.2 Retarget the theme-bar skin rules in `design-system/source/zoo/sections/theme-bar.mjs` from `body:has(#th-…:checked)` to `:root:has(#th-…:checked)` so role overrides land on the element that carries the built token declarations (per design decision 2).
- [x] 3.3 Replace the hardcoded halftone colour in `design-system/source/zoo/styles/components.css` (`.btn::before`, `rgb(31 27 22)`) with `var(--color-ink)`.
  > Note: for the halftone to *change* under a demo skin (asserted by 3.6), each skin in `data/skins.mjs` now also overrides `color-ink` (set to the skin's ink — the same value as its `color-text-default`). Without it, no skin touched the `color.ink` primitive the halftone (and `color.surface.ink`) chains bottom out at, so the dot screen and inverted ink surfaces stayed cream-ink. This is the "participates in a reskin" intent of design decision 4; the zoo can re-point to a proper role when `complete-the-colour-role-contract` ships one.
- [x] 3.4 Extend `test/showcase.test.mjs` with `zoo source does not re-link built tokens`: no zoo style/section source declares a custom property whose name collides with a built token name (assert against the manifest's derived names, allowing the zoo-local `--wx-*` effect vars) — covers the inspection half of scenario "The swap cascades through the built output alone".
- [x] 3.5 Extend `test/showcase.test.mjs` with `component styles carry no hardcoded colour`: `components.css` contains no colour literals (`rgb(`/`#hex`) outside `var()` fallbacks — covers the halftone clause of scenario "Components styled from tokens".
- [x] 3.6 Browser-driven check `theme swap restyles components via built CSS` (extends the check from 1.4 or the zoo baseline harness): open `dist/zoo/index.html`, activate each demo skin, and assert buttons, fields, cards, badges, links, and the button halftone change computed colour while layout and typography stay identical — covers scenarios "The reskin is shown by swapping only colour roles" and "The swap cascades through the built output alone" (behavioural half). Verify the demo remains labelled illustrative — covers "Demo skins are not misrepresented as shipped tokens".
  > Note: implemented with the same hand-rolled computed-value harness as 1.4 (no browser dependency in the repo): for every skin block in the built `dist/zoo/index.html`, component colour vars (button text, halftone `--color-ink`, field text, card surface, badge text, link hover) are computed against the page's `:root` declarations plus the skin's `:root:has()` override and must differ from cream, while computed typography/spacing stays byte-identical and skin blocks declare no type/space/size/radius/font override. The in-browser visual pass is left to the human per repo rules.
